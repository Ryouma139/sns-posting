# セッションと補足メモ

ログインと連携のセッションの違い、表示回数の意味、今後の分析メニューの案のまとめ。

- 機能ごとの仕様は [app-features.md](app-features.md)、Threads の連携手順は [threads-api.md](threads-api.md)、ログイン認証の設定は [cloudflare-access.md](cloudflare-access.md) を参照。

## 1. 2つのセッション

このアプリには「24時間」の設定が2つあり、役割がまったく違う。

| | ① Cloudflare Access のセッション | ② Worker のセッション |
|---|---|---|
| 何のためか | **アプリを開くためのログイン**(メールアドレス + 6桁のコード) | **Threads / X の連携情報**(トークン)の保存 |
| Cookie | `CF_Authorization` | `sns_session` |
| 設定する場所 | **Cloudflare ダッシュボード(Zero Trust)** | **コード**: [worker/index.js](../worker/index.js) の `sessionTtl = 86400` |
| 期限が切れると | ログイン画面が出る | 連携が外れて「未連携」になる |

2つは独立している。Access のログインが切れても連携は残り、連携が切れてもログインは残る。

## 2. Cloudflare Access のセッション(ログイン)

### 2回目からログイン画面が出ない理由

```text
1回目: サイトを開く → ログイン画面 → メールアドレス → 6桁のコード(One-time PIN)
         ↓ 認証に成功
       ブラウザに Cookie「CF_Authorization」を保存(24時間有効)

2回目以降: Cookie があればログイン画面を出さずに開く
```

正常な動作。24時間たつと、またログイン画面が出る。

### ログイン画面をもう一度確認したいとき

| 方法 | 内容 |
|---|---|
| **シークレットウィンドウで開く**(おすすめ) | Cookie がない状態で開ける |
| ログアウトする | `https://sns-posting.tryoma0227.workers.dev/cdn-cgi/access/logout` を開くと Cookie が消える |
| Cookie を削除する | ブラウザの設定で、このサイトの Cookie を消す |
| 別のブラウザ・スマホで開く | Cookie はブラウザごと |

### セッション期間を設定する場所

Worker のコードではなく、**Access(Zero Trust)側**で決まる。細かい設定ほど優先される。

| 優先 | 場所 | 内容 |
|---|---|---|
| 1 | Access → Applications → `sns-posting - Cloudflare Workers` → **Policies** → 各ポリシーの Session duration | ポリシーごと |
| 2 | Access → Applications → `sns-posting - Cloudflare Workers` → **Session Duration** | アプリごと(今は24時間) |
| 3 | Settings → Authentication → **Global session timeout** | Zero Trust 全体 |

変えるときは基本的に 2 を変える。ポリシー側に期間があればそちらが優先。短いほど安全だが、ログインの回数が増える。自分ひとりなら24時間で十分。

## 3. Worker のセッション(連携情報)

### 仕組み

ブラウザごとに、Threads / X の連携情報をサーバー側(KV)に保管する。

```text
ブラウザ                               Worker                     KV(SESSIONS)
  │ /api/... にアクセス                  │                          │
  │ Cookie: sns_session=ランダムなID ──→ │ ID で KV を読む ────────→ │ session:ID = { threads: {トークン, ユーザー名…}, accessToken(X)… }
  │                                      │ ←── 連携情報 ──────────── │
  │                                      │ そのトークンで Threads / X API を呼ぶ
```

- ブラウザに保存するのは**ランダムな ID だけ**。トークンは KV に置き、ブラウザには渡さない。
- 予約投稿のアカウント確認や、API 呼び出し回数のユーザー ID も、ここに保存した情報を使う。

| 処理 | 場所 | 内容 |
|---|---|---|
| 読み込み | `loadSession` | Cookie の ID で KV を読む。なければ新しい ID を作る |
| 保存 | `finish` | 内容が変わったときだけ KV に書き、期限を24時間後にする。新しいセッションのときは Cookie を発行する |
| 期間 | `sessionTtl = 86400` | KV の期限と Cookie の期限の両方 |

期限が切れると新しい空のセッションになり、Threads も X も「未連携」に戻る。

### 課題: 連携が24時間で切れる(未対応)

- Cookie は**最初に作ったときだけ**発行している(`if (session.isNew)`)。そのため、**最初のアクセスから24時間で必ず切れる**。毎日使っても延長されない。
- 一方、Threads の長期トークンは**約60日**有効。トークンはまだ使えるのに、セッションが先に切れて毎日連携し直すことになる。

修正案:

1. `sessionTtl` を長くする(例: 30日)
2. アクセスのたびに Cookie と KV の期限を延長する

KV の延長を毎回すると書き込みが増える(無料枠 1日1,000回)ため、「最後の延長から1日以上たっていたら延長する」形にする。

## 4. 表示回数とは

**アカウントの投稿が、誰かの画面に表示された回数**(impressions / views)。

- **人数ではなく回数**。同じ人が3回見れば3回。
- アカウントの**すべての投稿の合計**。古い投稿が今日見られた分も入る。
- 反応(いいね等)がなくても、画面に出れば1回。

### API の上限との関係

```text
24時間に呼べる回数 = 4,800 × 表示回数(10未満は10として計算)
```

| 直近24時間の表示回数 | 呼び出しの上限 |
|---|---|
| 0〜10回 | 48,000回(最低保証) |
| 100回 | 480,000回 |
| 1,000回 | 4,800,000回 |

投稿一覧の読み込みは1回で21回呼ぶが、最低保証でも1日2,000回以上読み込めるため、個人で使う範囲では上限に届くことはまずない。

- アプリで表示しているのは、アカウント単位の insights(`/{ユーザーID}/threads_insights?metric=views`)の直近24時間の値。
- 分析画面の投稿ごとの「表示回数」(`view_count`)は投稿1件分。こちらはアカウント全体。
- insights は日単位の集計で反映に時間がかかるため、Meta が上限の計算に使う値とは少しずれることがある。目安として見る。

## 5. SNS 分析のメニュー案(未実装)

### 今の権限とデータですぐ作れるもの

| メニュー案 | 内容 | 使うデータ |
|---|---|---|
| **ベストな投稿時間** | 曜日 × 時間帯ごとの平均いいね・表示回数をヒートマップで表示 | 取得済みの投稿の日時 + insights |
| **エンゲージメント率** | (いいね + 返信 + リポスト) ÷ 表示回数 を投稿ごとに計算 | insights(`views` は取得済み) |
| **投稿の傾向分析** | 文字数・ハッシュタグ・画像の有無・質問形式などで分類し、平均の反応を比べる | 本文 + insights |
| **アカウント全体の推移** | 表示回数・いいね・フォロワー数などを期間を指定して表示 | `/{ユーザーID}/threads_insights`(`threads_manage_insights` で取得済み) |
| **フォロワー属性** | 国・都市・年齢・性別の割合 | `follower_demographics`。**フォロワー100人以上**のときだけ |
| **X と Threads の比較** | 同じ期間の反応を並べる | 両方の投稿一覧。X は読み込みに料金がかかる可能性あり |
| **CSV エクスポート** | 分析データをダウンロード | 取得済みのデータ |

### 仕組みの追加が必要なもの

| メニュー案 | 必要なもの |
|---|---|
| **フォロワー数の推移グラフ** | Threads は今の数しか返さないため、毎日記録する仕組み(Cron Trigger + KV / D1) |
| **長い期間の分析** | 20件より前の投稿と数値をデータベースに保存([roadmap-database.md](roadmap-database.md) と関係) |
| **週・月ごとの比較レポート** | 過去の数値の保存 |
| **返信の分析** | `threads_read_replies` 権限の追加(自分の投稿への返信なら開発モードでも取れるはず) |
| **目標(KPI)管理** | 目標の保存場所と推移のデータ |

### 審査が必要なもの(保留中)

| メニュー案 | 必要な権限 |
|---|---|
| 競合アカウントの分析 | `threads_profile_discovery` |
| キーワードの話題量の推移(他人の投稿) | `threads_keyword_search` のアドバンスアクセス |

### おすすめの順番

1. **ベストな投稿時間**と**エンゲージメント率**(追加の権限も保存も不要)
2. **アカウント全体の推移**と**フォロワー属性**(今の権限で取れる)
3. **フォロワー数の推移**と**長い期間の分析**(Cron Trigger とデータベースを入れるときに、予約投稿の自動化と一緒に)

分析のもとになる投稿は今は**最新20件だけ**なので、件数が少ないうちは参考程度になる。
