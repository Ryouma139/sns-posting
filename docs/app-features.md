# アプリの機能と仕様

ダッシュボードの各機能の仕組みと制限のまとめ。Threads API の連携手順は [threads-api.md](threads-api.md) を参照。

## 1. API 利用状況の画面

サイドバーの「**API利用状況**」(`#usage`)で、Threads の投稿・返信の上限と直近24時間の消費数を表示する。

- Worker の `GET /api/threads/usage`(`threadsGetUsage`)が、Threads の `GET /{ユーザーID}/threads_publishing_limit?fields=quota_usage,config,reply_quota_usage,reply_config` を呼ぶ。返信の項目が取れなければ投稿の項目だけで取り直す。
- 画面を開いたとき、「最新に更新」を押したときに取得する(1回 = Threads API 1回)。
- API 呼び出し回数の上限(24時間で 4,800 × 表示回数)の残りは API から取得できないため、表示していない。
- X は Developer Portal の Usage で確認する。
- 上限と消費数は**アカウントごと**(複数アカウントの合計ではない)。画面には連携中のアカウント1つ分を表示する。別アカウントの分は、そのアカウントで連携し直して見る。
- 数えられるのは **API で投稿した件数**。Threads アプリから手で投稿した分はおそらく含まれない(同じアカウントで別の API アプリから投稿した分は含まれる)。
- Cloudflare の無料プランは、枠を超えても自動課金されず、エラーで止まる。

### 「投稿・返信の上限」と「API呼び出しの合計」の切り替え

画面上部のタブで切り替える。

| タブ | 表示 | 取得元 |
|---|---|---|
| 投稿・返信の上限 | 投稿 250件・返信 1,000件に対する直近24時間の件数 | `threads_publishing_limit`(Threads が数えた値) |
| API呼び出しの合計 | このアプリの呼び出し回数 / 上限(4,800 × 表示回数)、表示回数、Meta の使用率、種類ごとの内訳 | 下の仕組み |

- **呼び出し回数はこのアプリで数える**。Worker の `threadsFetch` が呼ぶたびに種類(投稿一覧・インサイト・投稿・検索・利用状況・プロフィール・連携)ごとに数え、リクエストの最後に KV へまとめて保存する(`saveThreadsCalls`。**KV の書き込みは画面の操作1回につき1回**)。
- KV のキーは `threads-calls:{ユーザーID}`。1時間単位で48時間分を残し、3日で自動的に消える。直近24時間の合計は1時間単位の概算。
- **上限**は、アカウントの表示回数(`/{ユーザーID}/threads_insights?metric=views`、直近24時間)× 4,800。10未満は10として計算する。取れなければ表示しない。
- **Meta の使用率**は、Threads が返す `X-App-Usage` ヘッダー(呼び出し・CPU・処理時間の %)。呼び出しが多くなったときだけ返るため、ないときは「余裕あり」と表示する。
- 数えられるのは**このアプリから呼んだ分だけ**。同じアカウントで別のアプリから呼んだ分は含まれない。上限は Meta の仕様で**アプリとアカウントの組み合わせごと**。
- 画面の一番下に「**参照URL**」として、次の出典と Threads の投稿(`threads_publishing_limit`)のページを表示する(`usageReferences`)。
- 参考: [Threads API の概要(レート制限)](https://developers.facebook.com/documentation/threads/overview)、[Graph API のレート制限(X-App-Usage)](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)

## 2. 取得件数(最新20件)

- 固定値。[src/App.jsx](../src/App.jsx) の `archiveLimit`、[worker/index.js](../worker/index.js) の Threads `limit=20` と X `max_results: '20'` の3か所。変えるときはそろえる。
- 分析画面の見出しは、実際に集計した件数を表示する(いいね数を取れなかった投稿は集計から外れるため、20件より少ないことがある)。
- Threads は投稿1件ごとに insights を1回呼ぶ。Workers 無料プランのサブリクエスト上限(1リクエスト50回)があるため、**40件程度まで**が安全。

## 3. 予約投稿(自動投稿)

予約は Worker の **D1(`DB`、データベース名 `sns-posting`)** に保存し、Cloudflare の **Cron Trigger** が**毎分**、予定時刻を過ぎた予約を投稿する。ブラウザを閉じていても投稿される。

```text
作成画面「予約投稿」→ POST /api/schedules → D1 の scheduled_posts に保存(status: pending)
                                              ↓ 毎分(wrangler.jsonc の triggers.crons)
                               scheduled() → runDueSchedules() → 予定時刻を過ぎたものを投稿
                                              ↓
                               status: posted(投稿済み)/ failed(投稿できませんでした)
```

- 本文・Threads のトピックタグ・**画像(4枚まで)**を予約できる。画像は **R2** に保存する(下の「予約の画像」)。
- 投稿は予定時刻から**1分ほど遅れる**ことがある(毎分の実行のため)。1回の実行で投稿するのは10件まで。残りは次の分に投稿する。
- 予約は D1 にあるので、**別のブラウザ・スマホでも同じ予約が見える**。ただし開発(`wrangler dev`)の D1 は PC 上の仮のもので、本番とは別。

### KV ではなく D1 にした理由

| | KV | D1(採用) |
|---|---|---|
| 書き込みの反映 | 最大60秒かかる。毎分の実行で同じ予約を2回投稿するおそれがある | すぐ反映される |
| 毎分の確認 | 一覧の取得(list)は無料枠が1日1,000回で、毎分(1日1,440回)だと足りない | SQL 1回。読み込みの無料枠は1日500万行 |

二重投稿を防ぐため、投稿の前に `status` を `pending` → `posting` に変える。変えられたときだけ投稿する(`runSchedule`)。

### 投稿に使うトークン

ブラウザのセッション(KV、24時間)が切れても投稿できるよう、トークンを**アカウントごとに D1 の `accounts` に保存する**。

| いつ保存するか | 内容 |
|---|---|
| 連携したとき(`xCallback`、`threadsCallback`) | 上書きする |
| 予約したとき | `accounts` になければ追加する(自動投稿の対応前に連携したセッション向け) |

- **X**: アクセストークンは約2時間で切れる。投稿のときに切れていれば `refresh_token` で更新し、新しいトークンを保存する(`xAccessToken`)。
- **Threads**: 長期トークンは約60日。残りが7日を切ったら更新する(`threadsAccessToken`)。期限が切れていたら、連携し直すまで投稿できない。Threads の呼び出しは API利用状況の画面の回数にも数える。
- **連携を解除しても、予約済みの投稿は投稿される**(別のアカウントに切り替えるために解除することがあるため)。止めたいときは予約を削除する。
- トークンは KV のセッションと同じく、暗号化せずに保存している。Cloudflare Access でサイトを守っている前提。

### 画面での表示

| 表示 | 状態 | できること |
|---|---|---|
| 予約済み | `pending`(予定時刻の前) | 今すぐ投稿・削除 |
| 投稿中 | `posting`、または予定時刻を過ぎて投稿を待っている | ― |
| 投稿済み | `posted`。7日たつと一覧から自動で消える | 一覧から消す |
| 投稿できませんでした | `failed`。理由を下に表示する | もう一度投稿・削除 |

- 一覧は概要画面を開いたときと、「更新」を押したときに読み込む。
- 「今すぐ投稿」は、**予約したアカウントのトークン**で Worker が投稿する(`POST /api/schedules/{ID}/post`)。そのアカウントを連携していなくてよい。
- 10分以上「投稿中」のままのものは「投稿できませんでした」にする。投稿されたかどうかは SNS で確認する。
- 連携中のアカウントの予約を上に、ほかのアカウントの予約を `@ユーザー名` 付きで下に表示する(今までと同じ)。

### 以前の予約(localStorage)

自動投稿に対応する前の予約は、ブラウザの localStorage に残っている。

- **予約したアカウントを連携すると、自動で D1 に移る**。予定時刻を過ぎていたものは自動では投稿せず、「投稿できませんでした」として移る(「もう一度投稿」で投稿できる)。
- 移せないもの(別のアカウント、アカウントの記録がない古い予約)は「このブラウザだけの予約(自動投稿されません)」と表示する。今までどおり手で「今すぐ投稿」を押す。

### API

| API | 内容 |
|---|---|
| `GET /api/schedules` | 予約の一覧(すべてのアカウント) |
| `POST /api/schedules` | 予約する(`platform`、`text`、`topicTag`、`scheduledAt`)。連携中のアカウントで予約する |
| `DELETE /api/schedules/{ID}` | 削除する(投稿中は 409) |
| `POST /api/schedules/{ID}/post` | 今すぐ投稿する |

### 開発環境で試す

`wrangler dev` は Cron を自動では動かさない。`npm run dev` を起動したまま、次の URL を開くと1回分を実行できる(`--test-scheduled` を付けてある)。

```bash
curl "http://127.0.0.1:8787/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"
```

`/__scheduled` は画面のファイルの配信(SPA)に吸い込まれるため使えない。開発の D1 の中身は `npx wrangler d1 execute sns-posting --local --command "SELECT * FROM scheduled_posts"` で見られる。

### 無料枠

| 項目 | 使う量 | 無料枠 |
|---|---|---|
| Cron Trigger | 1つ | 5つ |
| Workers のリクエスト | 毎分1回(1日1,440回) | 1日10万回 |
| D1 | 毎分 SQL 3つ。書き込みは予約・投稿のときだけ | 読み込み1日500万行、書き込み1日10万行 |

テーブルは Worker が最初に使うときに作る(`ensureSchema`)。マイグレーションのコマンドは不要。あとから足した列(`images`)は、すでにあるテーブルに `ALTER TABLE` で追加する(`addedColumns`)。

### 予約の画像

```text
「予約投稿」(画像あり)→ multipart/form-data で POST /api/schedules
  → 画像を R2 の media/{ID} に保存し、D1 の images に { origin, ids } を記録
予定時刻 → X:       R2 から読んで POST /2/media/upload → 投稿に付ける
           Threads: {origin}/api/media/{ID} の URL を渡す(Meta が取りに来る)
投稿済み → R2 の画像を消す
```

- 画像の保存先は **R2(`MEDIA`、バケット名 `sns-posting-media`)**。KV より保存できる量が多く(無料で10GB)、期限を気にせず予定時刻まで置いておける。
- R2 には自動で消える期限がないため、**投稿できたとき・予約を削除したときに消す**。「投稿できませんでした」の予約は、「もう一度投稿」のために残す。
- 画像付きの予約は、1回の実行で**1件だけ**投稿する。Threads は画像の処理を待つ間に何度も API を呼ぶため、1回の実行で外部を呼べる上限(50回)を超えないようにしている。残りは次の分に投稿する。
- Threads の画像付きの予約は、今すぐ投稿と同じく**開発環境(localhost)ではできない**。
- 一覧には画像の枚数を表示する。

## 4. 下書き

- 予約投稿と同じく、作成したアカウントを保存する(保存にはアカウントの連携が必要)。
- 一覧は連携中のアカウントの下書きを上に、ほかのアカウントの下書きを `@ユーザー名` 付きで下に表示する。
- 別アカウントの下書きを開こうとしたり保存しようとしたりすると、エラーを出して開かない。削除はできる。
- アカウントが記録されていない古い下書きは開けて、保存したときに連携中のアカウントのものになる。

## 5. トレンド検索

サイドバーの「**トレンド検索**」(`#trends`)で、キーワードを含む Threads の投稿を検索する。

- Worker の `GET /api/threads/search`(`threadsSearch`)が、Threads の `GET /keyword_search` を呼ぶ。権限は `threads_keyword_search`(連携時の scope に追加済み。**権限を追加したあとは連携し直す**)。
- 並び順: 人気順(`search_type=TOP`、Threads が人気と判断した順)/ 新着順(`RECENT`)。期間: 24時間・7日・30日以内(`since`)/ 指定なし。1回25件まで。
- **ほかの人の投稿のいいね数は API で取得できない**ため、「いいねが多い順」や「いいねがある投稿だけ」には絞れない。人気順+期間で代わりにする。
- **審査(アドバンスアクセス)を通過するまでは、連携中のアカウント自身の投稿だけが検索される**。ほかの人の投稿を出すには App Review が必要。
- 検索1回 = Threads API 1回。キーワード検索の上限は1アカウント24時間で2,200回程度。
- Threads のトレンド(話題のキーワード一覧)を取得する API はない。

### 取得できる範囲

開発モードでは、検索に限らず**トークンの持ち主(連携中のアカウント)の投稿しか取得できない**。開発モードの間のトレンド検索は「自分の過去の投稿をキーワードで探す機能」になる。

| 取得したいもの | 開発モード(今) | 審査通過後 |
|---|---|---|
| 連携中のアカウント自身の投稿 | ✅ | ✅ |
| テスターに登録したほかのアカウントの投稿 | ❌(そのアカウントで連携し直せば、その分だけ取れる) | ✅ |
| 関係のない他人の公開投稿 | ❌ | ✅ |

他人の投稿を取る権限は、どちらも審査が必要。

| 権限 | できること |
|---|---|
| `threads_keyword_search` | キーワードで公開投稿を検索する |
| `threads_profile_discovery` | ユーザー名を指定して、公開アカウントのプロフィール・投稿を取得する |

スクレイピングは Threads の利用規約違反になるため使わない。

## 6. 通知

- 保存件数の上限は **50件**([src/App.jsx](../src/App.jsx) の `notificationLimit`)。新しい通知を先頭に追加し、超えた分は古いものから消す。
- 表示件数は別に絞っていない。保存されている分(最大50件)をすべて通知パネルに表示する。
- SNS・アカウントで分けず、まとめて50件。localStorage に保存する(予約・下書きと同じく、開発と本番では別)。

## 7. 画像の添付

作成画面の画像ボタンで、投稿に画像を付けられる。

- JPEG・PNG、1枚5MBまで、**4枚まで**(X と Threads の両方で使える範囲)。値は [src/App.jsx](../src/App.jsx) と [worker/index.js](../worker/index.js) の `maxImages`・`maxImageBytes`・`imageTypes`。変えるときはそろえる。
- 画像があるときは、画面から Worker へ `multipart/form-data`(`text`、`accountId`、`topicTag`、`images`)で送る。テキストだけなら今までどおり JSON。
- 画像だけの投稿もできる(本文は空でよい)。
- **下書きには画像を保存しない**(localStorage に入りきらないため)。保存すると「画像は保存されません」と表示する。
- **予約には画像も保存する**(R2。3章の「予約の画像」)。

### X

- 画像ごとに `POST /2/media/upload` でアップロードし、返った ID を投稿の `media.media_ids` に付ける。**アップロードもクレジットを消費する**。
- 連携の scope に `media.write` を追加した。**追加前に連携したトークンでは画像を投稿できないため、連携し直す**(403 のときは画面にもそう表示する)。

### Threads

- Threads は画像を URL で受け取り、Meta のサーバーがその URL から画像を取りに来る。そのため Worker が画像を **R2(`MEDIA`)に保存**し、`/api/media/{ランダムな32文字}` で返す。今すぐ投稿の画像は、公開し終わったら消す。
- 1枚なら `IMAGE`、2枚以上なら `CAROUSEL`(各画像のコンテナ → まとめるコンテナ → 公開)。Meta が画像を取り込むまで公開できないため、コンテナの `status` が `FINISHED` になるまで待つ(最大10回、1.5秒おき)。
- `/api/media/*` はセッションを作らない(Meta のアクセスで KV の書き込みを増やさないため)。画像1枚につき R2 の書き込み1回・削除1回。
- 以前は KV に1時間だけ保存していた。予約の画像を予定時刻まで置いておくため、R2 にそろえた。
- **開発環境(localhost)では使えない**。Meta から localhost に届かないため、Worker がエラーを返す。
- **本番では Cloudflare Access の Bypass が必要**。サイト全体が Access で守られているため、そのままでは Meta が画像を取りに来られず投稿に失敗する。Zero Trust でアプリケーションを追加し、パス `sns-posting.tryoma0227.workers.dev/api/media/*` に **Bypass(Everyone)** のポリシーを付ける。URL はランダムで、投稿し終わると消えるため、公開しても推測されにくい(予約の画像は予定時刻まで残る)。

## 8. ハッシュタグ・トピックタグ

作成画面の `#` ボタンの動きは SNS によって違う。

| SNS | `#` ボタン | タグの送り方 |
|---|---|---|
| X | 本文のカーソル位置に `#` を入れる(直前が空白でなければ、空白を1つ入れてから `#`) | 本文に書いたものがそのままハッシュタグになる |
| Threads | 本文の下の「トピックタグ」欄にフォーカスを移す | 欄の値を `topic_tag` として送る。**本文には表示されない** |

### Threads のトピックタグ

- **1投稿に1つ**。1〜50文字、`.` と `&` は使えない。先頭の `#` は付けても外す。
- 画面([src/App.jsx](../src/App.jsx) の `topicTagError`)と Worker([worker/index.js](../worker/index.js) の `validateTopicTag`)の両方で同じ条件を確認する。条件に合わなければ、画面では「今すぐ投稿」「予約投稿」を押せず、Worker は 400 を返す。変えるときはそろえる。
- 画面から Worker へは `topicTag` として送る(JSON でも `multipart/form-data` でも)。X に投稿するときは空文字を送る。
- テキストだけ(`TEXT`)・画像1枚(`IMAGE`)・複数枚(`CAROUSEL`)のどれでも付けられる。カルーセルでは本文と同じく、まとめるコンテナにだけ付ける。
- 本文に `#〜` と書くと、Threads でもタグとして扱われるが**本文にもそのまま残る**。本文に `#〜` があると、タグ欄の下にその注意を表示する(`hasInlineTag`)。
- **下書き・予約にもタグを保存する**(画像と違い保存できる)。自動投稿のときも `topic_tag` として送る。一覧には `#タグ` を表示し、下書きを開くとタグ欄に戻る。投稿・予約・新規作成のあとはタグ欄を空にする。
- プレビューにはタグを本文の下に表示する。

## 9. App Review(審査)— 保留中

ほかの人の投稿を検索するには、`threads_keyword_search` のアドバンスアクセスが必要。**今は申請を保留している**。基本の流れは [threads-api.md](threads-api.md) の4章「ライブにする場合」。ここではそれ以外に必要なことをまとめる。

### 申請前の準備

- プライバシーポリシー・データ削除・利用規約のページは**誰でも開ける場所**に置く。本番サイトは Cloudflare Access で守られているため、そのページだけ Access の Bypass ルールで公開するか、GitHub Pages など別の場所に置く。
- 申請する権限に `threads_keyword_search` も含める。
- 各権限を、テスターのアカウントで申請前に一度ずつ実際に使っておく(投稿、一覧、いいね数、検索)。
- 使っていない Instagram のユースケースは外しておく(審査の対象が減る)。
- アドバンスアクセスでは、ビジネス認証や本人確認を求められることが多い。

### 用途の説明(例)

| 権限 | 説明 |
|---|---|
| `threads_basic` | ユーザー本人のプロフィールと投稿一覧をダッシュボードに表示する |
| `threads_content_publish` | ダッシュボードで作成したテキストを、ユーザー本人の Threads に投稿する |
| `threads_manage_insights` | ユーザー本人の投稿のいいね・返信・表示回数を分析画面に表示する |
| `threads_keyword_search` | ユーザーが入力したキーワードを含む公開投稿を表示し、投稿のネタ探しに使う |

### 動画とテスト手順

- 権限ごとに、**実際に使っている場面**を映す(連携 → 許可画面で権限が見える → 許可 → その機能を使う)。
- 画面が日本語なので、**英語の字幕・注釈**を付ける。テスト手順も英語で書く。

### 審査担当者のアクセス

- Cloudflare Access のままだと担当者がアプリを開けず、差し戻される。審査の間だけ Access を外すか、担当者が入れるルールにする。
- 外している間は誰でも開けるため、KV の書き込みや X API のクレジットが使われる可能性がある。審査が終わったら戻す。

### よくある差し戻し

- 動画にその権限を使う場面が映っていない
- 担当者がアプリを開けない・ログインできない
- プライバシーポリシーが開けない、内容が足りない
- 用途の説明があいまい
- 個人用ツールで、誰のためのアプリかがはっきりしない
